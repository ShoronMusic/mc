# AI 協業診断 — 活用指標と継続改善

musicaichat（MC）プロジェクトにおける **指示者（プロダクトオーナー）とコーディング AI の協業** を、定期的に振り返り、改善するための指標書。

初版: 2026-06-07（[Zenn: AI は認識態度を増幅する](https://zenn.dev/pdfractal/articles/373be6a9de3e8c) を踏まえた初回診断）

---

## 目的

- AI の出力品質ではなく、**判断主権を自分の手元に残せているか** を測る
- セッションごとに「進んだ感」と「理解の深さ」のズレを可視化する
- コーディング AI が **忖度なく** 改善点・姿勢を指摘するための共通言語を持つ

---

## 理論の骨格（診断の前提）

知能そのものではなく **認識態度** が増幅される。

| 増幅される良い側 | 増幅される危ない側 |
|------------------|-------------------|
| 違和感が消えるまで問い直す | それっぽい答えで止まる |
| 検証・比較・言い換えに再投資 | 思考省略に再投資 |
| 自己説明（自分の言葉で再構成） | AI の説明を読んだ＝分かった |
| 失敗時の説明責任を自分が持つ | 多数派・権威の代理として使う |

**差が広がる本当の理由:** 一回ごとの **思考停止条件** が学習される。

## 協業指標（5 軸・各 1〜5 点）

セッション終了時または週次で、主観＋事実で 1〜5 を付ける。  
**合計 25 点満点。目標は「毎回満点」ではなく、弱点軸の改善トレンド。**

### 1. 判断主権（Judgment Sovereignty）

| 点 | 基準 |
|----|------|
| 5 | 成功条件・禁止事項・ロールバック条件を **自分で先に書いた** うえで AI に依頼 |
| 4 | 実装前にプランを自分の言葉で要約し、AI 案と差分を確認した |
| 3 | AI の提案を採用したが、採用理由を 1 文説明できる |
| 2 | 「進めて」「続けて」が主で、採用理由は曖昧 |
| 1 | AI の結論をそのまま実行し、後から結果だけ見た |

### 2. 停止条件（Stopping Condition）

| 点 | 基準 |
|----|------|
| 5 | **腑に落ちるまで** 質問・反証・小さな検証（dry-run 等）をした |
| 4 | 不明点を 1 つ以上明示してから次へ進んだ |
| 3 | ビルド／validate 通過で止めた（コードの正しさは未確認） |
| 2 | タスク完了・デプロイ成功で止めた |
| 1 | AI の要約を読んで満足した |

### 3. 自己説明（Self-Explanation）

| 点 | 基準 |
|----|------|
| 5 | セッション後、**AI なしで** 変更内容・理由・失敗モードを 3 文で説明できる |
| 4 | ドメインルール（DB・Spotify・m8 等）は自分の言葉で書けた |
| 3 | AI の説明を読んで理解したつもり（自分では言い換えていない） |
| 2 | ログ・JSON の意味だけ把握し、設計は AI 依存 |
| 1 | 何を変えたか説明できない |

### 4. 再投資先（Cognitive Offload Reinvestment）

負荷を下げたぶんを **どこに** 使ったか。

| 点 | 基準 |
|----|------|
| 5 | 反例探索・前提点検・diff 理解・本番影響確認 |
| 4 | dry-run → 本番 → 数値比較のループ |
| 3 | lint / validate / test のみ |
| 2 | 「動いた」確認のみ |
| 1 | 確認せず次タスクへ |

### 5. 責任边界（Accountability Boundary）

| 点 | 基準 |
|----|------|
| 5 | 本番 DB・課金・秘密情報は自分実行 or 明示承認。Git ロールバック前提を宣言 |
| 4 | 手作業エッジケースを自分で指定・入力 |
| 3 | AI 実装だが validate とスモークは通した |
| 2 | AI に任せっきり（コミット・apply 含む） |
| 1 | 失敗時「AI が書いたから」で終わる |

## 初回診断スナップショット（2026-06-07）

ログ・`AGENTS.md`・ユーザールール・会話傾向からの **率直な位置づけ**（忖度なし）。

### 強み（記事の「賢い側」）

- **ドメイン判断は自分のもの**（Spotify 一致、feat./Remix、m8 の The 扱い、拒否リスト等）
- **データ品質への埸着**（バックフィル、partial_unresolved、手作業 26 曲）
- **安全弁**（「ストップ」、Git で戻す、自分の PowerShell で apply）
- **メタ投資**（Qiita → `AGENTS.md`・`ai-output-policy`・`npm run validate`）
- **プロダクト内 AI** では誤信対策を設計している（開発 AI より慎重）

### 弱点（改善優先）

1. **停止条件が「前に進んだ感」に寄るセッション**（「続けて」「進めて」連打）
2. **所有の単位がタスク完了**（機能は動くが、変更の失敗モードを自分で説明しにくい）
3. **探索・地図を AI/docs に委譲**（心臓部 3 ファイルが頭に残りにくい）
4. **開発 AI では CI 通過＝正しさの代理**になりがち

### 初回スコア（目安）

| 軸 | 点 | メモ |
|----|-----|------|
| 判断主権 | 4 | ルールは自分。実行委任が早い局面あり |
| 停止条件 | 3 | dry-run は良い。コード理解で止めないことがある |
| 自己説明 | 3 | ドメイン強、実装弱 |
| 再投資先 | 4 | validate・数値比較は良い。diff 理解は不足 |
| 責任边界 | 4 | DB は自分実行。コード変更は AI 比重高 |
| **合計** | **18/25** | 改善余地は「停止」と「自己説明」 |

## セッション前・中・後のルーティン

### 依頼前（30 秒）

```text
成功の定義（1 行）:
やらないこと（1 行）:
戻す条件（1 行）:
```

### 「進めてくれ」の直前

- AI が「良いプラン」と言ったら **反証 1 問**（最悪の失敗モードは？既存仕様と矛盾しない？）

### セッション後（1 分・自分用）

```text
今日変えたのは:
触ったファイルと理由:
まだ説明できないこと:
```

書けない項目があれば **まだ浅い** — 次セッションで AI に「言い換えて説明せよ」と頼む。

### 週次

- 心臓部のどれか 1 ファイルを **AI なし 15 分** 読む:  
  `src/lib/gemini.ts` / `src/lib/song-entities.ts` / `src/app/api/ai/comment-pack/route.ts`
- 本 doc の 5 軸を 1 回だけ採点し、前週と比較

## コーディング AI への継続指示

**以降の MC プロジェクトにおける会話では、コーディング AI は以下を行う。**

1. **忖度しない** — ユーザーの指示が早い停止・同調・責任委譲のパターンに入ったら、短く指摘する
2. **指摘のタイミング**
   - 「進めて」「続けて」「では実行」が **成功条件なし** で続くとき
   - 大きな実装（新 API・DB 変更・バッチ apply）の **前**
   - セッション終了時、**自己説明ができていなさそう** なとき（1 問だけ）
3. **指摘の形** — 説教長文にしない。次のいずれか 1 つ:
   - 「成功の定義 1 行を先に書いてください」
   - 「この変更の最悪の失敗モードは何ですか？」
   - 「セッション後、自分の言葉で 3 文説明できますか？」
   - 「ここは AI 実行より、あなたの PowerShell / 手確認向きです」
4. **褒めないため褒めない** — 良いパターン（ストップ、dry-run、手作業リスト、Git ロールバック宣言）を見たら **名指しで 1 行** 記録する程度にとどめる
5. **診断の記録** — 月 1 回またはユーザー依頼時、本 doc の「診断ログ」節を更新する
